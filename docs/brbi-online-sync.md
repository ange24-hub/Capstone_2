# One-time private BRBI online sync

This release transfers the user's existing November 8 BRBI archive data directly to the existing online server. Neither plaintext nor encrypted resident data is uploaded to GitHub. Only application code is deployed through Git. The approved transfer remains in ignored local storage and goes directly to the installation's HTTPS domain.

The container creates a dedicated RSA-3072 recipient key inside private persistent storage. HTTPS GET `/api/deployment-data-sync/brbi-20261108` publishes the public key and aggregate progress only. Local preparation encrypts the reviewed source plan with a random AES-256-GCM key wrapped using RSA-OAEP. The ciphertext is bound to the recipient key, fixed release and production hostname. Private keys and application secrets are never exported or published.

The temporary private transfer route accepted only the pinned SHA-256 of the reviewed encrypted payload. It required HTTPS, the exact production hostname, a short-lived receiver timestamp and an RSA/SHA-256 sender signature. Application passwords and APP_KEY were not used or transmitted. After staging, the upload route, sender verification key and transfer-only code were removed. Their audit copies and the sender private key remain solely in ignored laptop storage under `storage/app/deployment-data-sync/`. The sender verified TLS, refused redirects and used the authenticated receiver's clock because laptop and hosting clocks differ. No network endpoint can now upload a packet or start an import.

`scripts/prepare_encrypted_brbi_sync.php` reads the original private archive and an HTTPS-fetched recipient public key. It exports six previously missing consolidated barangay registries and all 29 barangays' NEW worksheet rows. Recipient barangay IDs are resolved by name. Original worksheet provenance and missing dates are retained. Whole workbooks and local database dumps are not transported.

On the next deployment, `brbi:sync-release` imports only the pinned packet from private persistent storage at the fixed production host. It locks and backs up all ten affected tables privately, appends missing identities, prepares unsigned missing RBI draft rows, and verifies existing records. Submitted forms remain byte-for-byte unchanged. Old draft rows remain an exact prefix; only draft rows and update timestamps may grow. Ambiguous identities are held for review. Existing residents, household fields, signatures, classifications, movements and form members cannot be overwritten or removed. A verification failure rolls back the transaction and leaves the website available.

Private backups, the source plan, detailed review and diagnostics are under `storage/app/deployment-data-sync/`. The public report contains only aggregate completion/preservation status and counts. A completed envelope is not reapplied on ordinary restarts; identity checks make a retry idempotent. A database restore performed independently of storage requires a fresh review of the completion marker before syncing again. No accounts are created, demo rows deleted, movement dates fabricated, or missing reporting dates guessed. Regenerating a ciphertext requires reviewing and repinning its hash before transfer.
